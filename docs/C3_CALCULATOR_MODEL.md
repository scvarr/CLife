# C3 — геномный калькулятор

Статус: **принято / реализованная текущая модель calculator core**

Этот документ заменяет более раннюю попытку строить ядро вокруг отдельных числовых ролей `Field / Resource / State / Matter / Measure / Property`.

C0 остаётся описанием первого клеточного мира и удобным предметным языком обсуждения. C2 фиксирует промежуточный этап проектирования. Если C0 или C2 конфликтуют с C3 в вопросах границы универсального core, приоритет имеет C3.

## 1. Основная идея

CLife core — небольшой детерминированный **геномный калькулятор**.

У объекта есть числовые значения:

```text
value[0]
value[1]
value[2]
...
```

Для core каждое значение — просто число по адресу. Сам core не знает, является ли оно светом, энергией, температурой, количеством материала, пропорцией формы или чем-либо ещё.

Первый world preset использует клеточную аналогию, поэтому на уровне мира и пользовательских инструментов значения получают понятные имена:

```text
Light
Energy
Temperature
Organic
Proportion
...
```

Имена нужны человеку и являются данными мира. Они не создают разные C++-типы и не меняют способ хранения числа.

## 2. Геном описывает способности объекта

Геном не является последовательной программой команд над состоянием.

Он описывает конечный вычислительный конвейер функций. Функция получает фактически доступное количество из входного значения и на основе полученного количества производит результат в следующем значении конвейера.

Концептуально:

```text
value A
   |
   | function takes available input
   v
value B
   |
   | next function
   v
value C
```

Внутри генома нет универсальных команд `SET`, `ADD` или специальных операций для `State`.

На текущем уровне базовое действие функции над входом — **взять доступное количество**, ограниченное её максимальной пропускной способностью за tick. Конкретная формула результата функции является данными/описанием функции первого мира и позднее должна выражаться компактным DSL.

## 3. Корневые значения приходят извне

Если у значения нет источника внутри геномного конвейера, его может задавать world/host/engine.

Например первый клеточный мир может передать:

```text
Light = 1
AmbientTemperature = 0.2
```

Для calculator это обычные числовые значения. Он не знает, что `Light` пришёл от лампы, а `AmbientTemperature` — от физического или графического движка.

Таким образом готовые возможности host/engine могут использоваться как источник части чисел мира без повторной реализации той же пространственной или физической работы внутри core.

## 4. Конкуренция за одно значение

Порядок записей функций в genome не задаёт приоритет.

Если несколько функций одновременно хотят взять одно ограниченное значение, они получают одинаковую долю своей потенциальной нагрузки.

```text
total_demand = sum(function demand)
load_fraction = min(1, available / total_demand)
actual_i = demand_i * load_fraction
```

Пример:

```text
Light = 1

Function A wants 1
Function B wants 1

A receives 0.5
B receives 0.5
```

Именно это правило заменяет последовательное «кто выполнился первым, тот и забрал ресурс» и снимает необходимость в imperative scheduler для такого конфликта.

## 5. Конечный same-tick конвейер

На текущем этапе геномный граф одного tick должен сводиться к конечному конвейеру зависимостей без same-tick циклов.

Это означает:

- порядок хранения записей genome не является порядком исполнения;
- структура зависимостей может быть подготовлена при формировании объекта;
- независимые ветви не требуют общей последовательной очереди;
- core не должен вводить сложный scheduler без отдельной необходимости модели.

Если будущая механика действительно потребует циклического same-tick расчёта, это будет отдельное изменение закона, а не скрытое усложнение текущего evaluator.

## 6. Остаток значения не является State

Core не переводит автоматически неиспользованный результат в специальный `State`.

После завершения геномного конвейера может остаться некоторое количество значения. Что с ним происходит дальше, определяют **правила мира**, а не genome и не встроенная категория числа.

Например в первом клеточном мире:

```text
Energy produced = 1.00
Energy used by genome functions = 0.25
unused Energy = 0.75
```

После работы генома world rule может определить:

```text
1 Energy = +0.1 Temperature
```

Тогда:

```text
Temperature delta = 0.75 * 0.1 = 0.075
```

Если правило мира учитывает материал клетки, формула может зависеть и от его числовых значений. Это всё равно world rule: клетка не обязана иметь геномную функцию «нагреться».

## 7. World rules — неизбежные последствия

Принцип разделения:

```text
Genome
    что объект умеет делать

World rules
    что неизбежно происходит с числами объекта/мира
```

World rules задаются определением мира и применяются независимо от конкретного genome там, где это предусмотрено миром.

Примеры первого клеточного мира могут включать:

```text
unused Energy -> Temperature change
Temperature change depends on cell material
external Light is supplied by world/engine
```

Эти примеры не становятся универсальными законами CLife core. Другой world preset может задать совершенно другие имена и правила.

## 8. Tick

Минимальная концептуальная схема tick:

```text
1. World/host/engine supplies external root values

2. Genome pipeline runs
       functions request input values
       shared demand is resolved proportionally
       actual inputs produce downstream values

3. End-of-tick world rules process consequences
       including unused values when the world defines such a rule

4. Resulting object/world values become the basis of the next tick
```

World rules не являются продолжением genome и не должны зависеть от порядка записей функций genome.

## 9. Топология организма

В первом клеточном мире организм является графом клеток.

Связь между клетками означает только соседство/принадлежность связной структуре. Сама связь не хранит длину, силу, упругость, ресурс или другие параметры только потому, что она существует.

```text
Cell A -- Cell B -- Cell C
```

Поведение обеспечивается значениями и функциями самих клеток.

Например средняя клетка может изменить собственное значение `Proportion`. Calculator видит только изменение числа. Host/engine интерпретирует это число как изменение геометрии клетки; поскольку соседние клетки визуально/физически склеены согласно topology, изменение формы может привести к движению всего организма.

Core не вводит для этого отдельные понятия `muscle`, `move`, `connection length` или `force`.

## 10. Граница с Godot/другим engine

Engine может одновременно быть:

- источником внешних чисел для calculator;
- потребителем рассчитанных чисел;
- реализацией геометрии, коллизий, гравитации и визуализации первого мира.

Calculator не обязан повторно вычислять то, что engine уже умеет предоставить как число.

В обратную сторону engine может интерпретировать значения объекта как параметры представления. Например `Proportion` может менять форму клетки, а другое значение — цвет или иной визуальный параметр.

Связь calculator и engine должна оставаться числовой: конкретная семантика binding принадлежит world preset/adapter, а не универсальному evaluator.

## 11. Что больше не является фундаментом core

Следующие категории были полезны как промежуточный язык проектирования первого клеточного мира, но больше не считаются фундаментальными сущностями calculator:

```text
Field
Resource
State
Matter
Measure
Property
Store
RemainderToState
```

Они могут существовать как человеческие понятия, editor-блоки или соглашения конкретного world preset, если это удобно пользователю.

Например UI первого мира вполне может показывать `Energy storage`, хотя runtime-представление такого поведения будет скомпилировано в более простой числовой конвейер.

## 12. Реализованное состояние

Компактный calculator реализован и сохраняет наблюдаемый эксперимент на простом числовом фундаменте.

Человеческий сценарий остаётся знакомым:

```text
Light
  -> клеточная функция
Energy
  -> часть используется клеткой
unused Energy
  -> world rule
Temperature change
```

Универсальный API не содержит искусственного деления чисел на `Field / Resource / State / Matter` и связанных с ним обязательных `Measure / Property` конструкций.

Первый клеточный мир остаётся тестовым world preset и предметным языком разработки, а core является компактной машиной для построения более общих эмерджентных систем. Редактируемая модель мира и host/runtime-граница описаны в `C4_HOST_WORLD_EDITOR_MODEL.md`.
